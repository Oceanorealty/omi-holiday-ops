# Property, staff and sandbox account workflows

Properties now support literal text/ID search, unit and website-publication filters, 25-row pagination and collapsed settings. Unit listings are individually reachable. Each property links directly to its gallery, custom fields, calendar and booking window.

The gallery stores up to 50 public HTTPS photo URLs, descriptions, captions, order, archive state and an explicitly selected cover. Changes require an actor-bound state token and reason and are audited. Archiving is reversible; select another cover before archiving the current one. Active photos appear in the published public listing API. This change does not host media, update the marketing website or publish photos to channels.

Named non-administrator accounts use `/my-work`: only their current assignments, task start/completion, required checklist checks, their own timers and their own evidence uploads. Current assignment and active account are checked on every request. Legacy management and financial routes require an administrator. Manager is currently an assigned-work role, not a separate management permission set. Shared administrator login remains supported. Staff creation and activation changes are audited; disabling preserves history and stops running timers. Self-disable and reuse of the shared administrator name are rejected. There is no hard-delete control.

Sandbox checkout keeps an opaque checkout identity in per-tab session storage before creating payment. Reload uses an authenticated resume endpoint and the original immutable snapshot and Stripe intent. Guest, card and client-secret data are not saved in session storage. Terminal recovery shows the original booking without mounting a payment form. A new verified sandbox success atomically creates its booking account, accommodation charge, payment entry, sandbox-labelled receipt and immutable origin link. Duplicate callbacks do not create a second account. Old confirmed payments are flagged for review rather than silently backfilled. This is not bank reconciliation or live payment activation.

Validation: 489 SQLite/PostgreSQL checks and five frontend logic scenarios. Local browser gallery add/audit, named worker login and assigned task start checked. Real Stripe Sandbox A$2 payment was resumed after a browser reload; its signed callback created one booking, one account link, one charge and one payment. Reload after confirmation returned the same booking without another card form. No real funds or production property records were used.

Deployment adds `property_photos` and `public_payment_accounts` tables. Keep payment checkout disabled in production. No credentials or runtime databases are included. Rollback can restore prior application code while retaining unused additive tables; note that prior versions do not provide the new global named-staff route restrictions. Full custom permissions, two-factor authentication, owner accounts, production payments and channel qualification remain separate work.
