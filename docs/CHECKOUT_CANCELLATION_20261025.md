# Verified sandbox checkout cancellation

Authenticated checkout bearers can cancel an unpaid test PaymentIntent. OPS verifies its persisted amount, currency, checkout metadata, intent ID and test mode; cancellation is offered only for requires_payment_method, requires_confirmation or requires_action with zero received/capturable funds. Only a verified provider canceled result releases the local inventory hold. This does not cancel confirmed reservations, capture authorizations, refund an ordinary completed payment, or enable live credentials.

Retries use the original creation parameters/key and a fixed cancellation idempotency key. An ambiguous intent missing its ID can be recovered for cancellation within the existing conservative 23-hour window, even after its lease expired; older unknown attempts require review. No stock write lock is held during Stripe calls. Verified cancellation atomically records the cancelled state and one existing OpsCommand audit entry; the hold record is retained. No schema change is needed.

Network-uncertain cancellations preserve the attempt and enter admin review immediately. Status/recovery flags suppress another browser payment and withhold a new client secret until the cancellation resolves. A racing success callback can confirm normally when cancellation was not verified. A contradictory success after verified cancellation follows the existing idempotent compensating refund path; a later replay of the original cancellation does not regress that refund state. Signed cancellation callbacks and status recovery also settle lost cancellation responses.

The phone UI places cancellation near the hold message, hides card entry after a terminal result, and enables Start another test booking only after a confirmed terminal state. The original identity remains in per-tab storage until then. Payment submission refreshes server status before calling Stripe. Closing a page alone never claims cancellation.

Validation: 599 tests passed with disposable PostgreSQL, including auth/config isolation, concurrent cancellation, stale recovery responses, lost creation/cancellation responses, old idempotency windows, callback races, malformed cancellation proofs and replay ordering. Real existing Stripe Sandbox browser acceptance created an independent synthetic local checkout without submitting a card, verified canceled/zero received/zero capturable, received a signed cancellation callback (HTTP 200), released inventory before lease expiry, retained one audit and no booking/account, and successfully re-quoted the same dates using a new browser identity. Width 390px, page width 375px. Final button placement was verified on the fresh form. No real money moved; local test services were stopped.

Production payments, live cancellation/refund workflows, OTA reservations and anti-abuse controls remain separate unfinished work. Before rollback to older checkout code, keep sandbox checkout disabled and reconcile cancelled attempts; older code does not interpret the new cancelled state. Preserve audit/payment records. Provider references: https://docs.stripe.com/api/payment_intents/cancel and https://docs.stripe.com/api/idempotent_requests .
