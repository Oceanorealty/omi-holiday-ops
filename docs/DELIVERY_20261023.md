## Implemented flows

- **Local reservations:** create, change dates/guest/amount, cancel/restore, source-aware editing, command deduplication, version-bound forms, reasons and immutable history. New direct reservations receive private portal links. Cleaning tasks follow edits transactionally; locked/completed work is retained for review.
- **Inventory and rates:** per-night price, minimum/maximum stay, arrival/departure closures, stop sell, reset, audit and optimistic version checks. Property minimum/maximum nightly rates clamp effective prices after rules/overrides. Manual pricing ignores dynamic rules; quote and public calendar share the calculation. Negotiated reservation amounts are not silently repriced.
- **Shared stock:** explicit physical-resource capacity and listing consumption. Whole-home listings can consume multiple room resources; split-room listings consume the same resources independently. Multi-unit room types use capacity. All attached resources are consumed, rather than treated as alternative room assignments. Default unmapped listings retain capacity one; legacy parent links do not automatically pool stock.
- **Inventory mutation coordination:** direct reservations, source observations, source cancellation reviews, manual blocks, request approvals and resource configuration use the same database guard. Imported over-capacity observations are retained and flagged. Weighted simultaneous usage permits turnover without counting disjoint bookings together. Resource timezone mismatches fail closed. Existing booking timezone changes require a reviewed migration.
- **iCal:** exports a rolling 730-day window of fully unavailable nights, including shared capacity and stop sell, without guest details. Partial room-type occupancy does not close remaining units. Configuration errors return retryable 503 rather than an empty availability feed. iCal polling is not real-time OTA synchronization.
- **Reservation requests:** signed expiring price quotes, guest contact capture, replay protection, pending list, approval/rejection. Approval rechecks price, restrictions and stock, then creates the booking and request link atomically. Pending requests do not reserve inventory; no instant checkout, deposit or payment is claimed.
- **Task plans:** immutable required-check templates copied into tasks/plans; fixed day intervals, inclusive end dates, pause/resume and bounded catch-up without skipping unprocessed dates. Concurrent generators create each occurrence once. Background generation runs only with the existing sync setting; sleeping hosting can delay it.
- **Task expenses:** known task cost creates one linked expense in the completion transaction. Required checks block premature completion. Reopening/recompleting does not create another charge. Posted task costs and generated expenses are protected from silent edits/deletion. This records expense, not payment; time/material line items remain pending.
- **Online arrival details:** per-booking names, phone, party size, expected local arrival, requests and house-rule snapshot acknowledgement. Date/status/rule changes invalidate forms; previous submissions remain. Submission is not actual attendance or identity verification.
- **Portal conversations:** guest questions, administrator replies, private internal notes, assignment, open/waiting/resolved state, per-user unread cursors and history pagination. Guest questions reopen resolved threads. Signed forms, per-stay rate limits and once-only append protect submission. Internal notes and administrator identity are excluded from guest views. Guests return to the portal to see replies; no email/WhatsApp/OTA notification or external delivery is implied. Assignment records responsibility; administrator access is currently required.
- **Private links:** create/replace guest links with audit; replacement revokes previous links/forms without deleting messages or arrival history. New direct bookings issue a link without sending it.
- **Reports:** property/date reserved/blocked/sellable nights, channel-night breakdown, known booking value prorated by night and CSV. Legacy amounts lack currency codes and use an explicit AUD assumption. Booking value is not receipts or accommodation-only revenue. Ratios for mapped stock are suppressed because this is not a physical-unit occupancy report. No portfolio double-sum or complete ADR/RevPAR is fabricated.
- **Readiness and channels:** feed/sync/timezone/staff checks; official Booking.com short-lived token exchange and read-only active-room discovery, tested with synthetic contracts only. Airbnb/Expedia display prerequisites. User confirmed no Booking.com machine account or Airbnb API eligibility. No live adapter success is simulated.

## Database and rollout

All new tables are additive: reservation/inventory audits and daily settings; generic command audits; task templates/applications/schedules/occurrences/costs; guest arrival details/events; property pricing bounds; reservation requests; stock guard/resources/bindings; portal conversations/messages/read cursors. Existing booking status enums are unchanged. The stock guard serializes inventory changes globally for this small PMS; this reduces concurrency throughput and is not a distributed OTA lock.

Startup snapshot schema is `ops_backup_20261023`; the prior helper default remains compatible. Same-database snapshots are not independent disaster recovery or complete sequence/schema restoration. Application health release is `ops-parity-20261023`.

Before production rollout: verify current upstream; pass CI; verify an independent database backup and application rollback; retain scheduler/message settings deliberately; deploy through the existing Render repository pipeline; verify health and authenticated database readiness.
